# 2026-11-19 实测：普通工作目录的跨主机续聊

此记录保留方法与经过，已省去真实账号目录、会话 UUID、业务设计内容、图片、源码和凭据。主机称为源 A 与目标 B。

## 需求与约束

迁移一段正在研究架构的 Codex 会话及过程中生成的文件。用户要求原会话继续工作，等它完成后迁移。源 cwd 是普通用户目录，其中的源码子目录是 Git 仓库。目标主机已连接到桌面端，但已保存项目目录位于只读挂载。

## 实际顺序

1. 用 `list_threads` 和 `read_thread` 确认唯一会话，取得源 ID、cwd 和运行状态。未向原会话发消息、未调用中断。
2. 只读检查两台主机、源 rollout、附件、设计稿和相关源码。查到内置跨主机 handoff 要求源 cwd 位于 Git 仓库；子目录存在 `.git` 不满足此条件，因此不调用 handoff 试错。
3. 用 `wait_threads` 等到最新轮 completed、会话 idle，再开始快照。最终第四份设计稿与完整最终回复都进入快照。
4. 复制 tracked/untracked 源码、普通 `.git`、ignored 目录中的必要第三方源码、四份设计稿、已引用的交接材料/结果摘要、3 张上传图片及完整 rollout。权重、数据、虚拟环境、编译依赖和无关输出不在本次迁移范围。
5. 在源创建 manifest 和压缩包。首次 scp 写入目标的已保存项目目录失败；检查 `statvfs` 确认只读挂载后，改用另一个现有用户目录下的新可写目录。没有 remount 或修改容器设置。
6. 经本机 `scp -3` 中转传输，在目标验证归档哈希并逐文件核验。原始 rollout 原样保留，另建路径重映射的导入副本，设计稿链接也指向新工作目录。
7. 在目标从二进制生成当前 schema，使用独立 `codex app-server --stdio` 连接。安装临时历史到目标规范 sessions 路径后，通过 list 注册，再按 ID fork。
8. 源 provider 在目标未配置，直接 resume 报错；fork 使用目标现有 provider/model，未改全局配置或复制密钥。返回的新 ID 保留全部历史，reasoning effort 保持 high，未启动新一轮推理。
9. 用 API 比较源/目标所有轮次的 ID、状态与条目 ID/type，抽查最新回复和附件。目标在桌面列表可见。临时的旧 ID 副本仅在目标机归档，源 A 原会话与原文件保留。
10. 项目归属工具先报 sidebar 尚不可用，触发标题/列表加载后又报无法安全判断源项目。记录为“聊天可见，未分配到已有只读项目”，没有手改 UI 全局状态。

## 失败尝试带来的修正

- 不能只将 rollout 放任意目录后直接 resume；该版本先要求可按 ID 找到规范记录。
- 注册之后继续携带导入临时路径会触发 paginated stale path；按 ID 导入即可。
- 目标 `realpath` 与用户常用别名路径不同，文本相等断言会误报失败。
- fork 后目标 rollout 的 `response_item` 数为 0，实际历史可从 API 完整读取。最终改用 API 比较，8 轮 169 个条目均一致。
- 不把 provider 缺失解释为登录失效，也不通过改全局设置解决线程级迁移。
- 手动路径复用有新旧前缀嵌套时不能连续 `.replace`；用最长匹配、一次替换，保留源件。

此案例证明当时环境中的路线可行，不证明所有 Codex 版本都使用同样的 canonicalization、分页存储和 RPC 参数；每次先检查当前 schema 与运行状态。
